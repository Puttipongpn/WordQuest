# Runtime Asset Structure Proposal

## Phase 71E Scope

This document proposes the eventual runtime file layout and naming rules. Phase 71E does not create `src/assets/`, move PNGs, add imports, create an asset manifest, or implement animation playback.

## Naming Rules

- Use lowercase snake_case filenames.
- Keep the current canonical file names to preserve QA/report traceability.
- Use `_sheet.png` only for horizontal spritesheets.
- Use `{category}_{identity}_{state}_sheet.png` for character animation sheets.
- Use `effect_{purpose}_sheet.png` for effects.
- Use `ui_{purpose}.png` for static UI assets.
- Use `background_{screen_or_context}_{variant}.png` for backgrounds.
- Do not add generated duplicate suffixes such as `(3)`, `(4)`, `copy`, or `final-final`.
- Do not encode frame count or dimensions in filenames; those belong in future metadata.

Suggested future metadata IDs use the filename stem without `_sheet` where applicable:

- `player_word_mage_idle`
- `monster_slime_attack`
- `elite_crystal_slime_hit`
- `boss_gatekeeper_defeat`
- `effect_fire`
- `ui_gold_coin`
- `background_dungeon_battle_01`

IDs must be stable and must not depend on import paths generated by the bundler.

## Candidate Copy Rules For Phase 71F

Phase 71F, if explicitly authorized, should copy rather than move accepted candidates into the proposed runtime tree.

Source precedence:

1. Gatekeeper attack comes from `normalized_assets_refined_targeted/bosses/gatekeeper/`.
2. Vocabulary card frame comes from `normalized_assets_refined_targeted/ui/`.
3. All other listed candidates come from `normalized_assets_refined_full/`.
4. Raw generated files under `Asset/` are never runtime import sources.

Copy verification should record source path, destination path, dimensions, file hash, and Human QA status. Original normalized candidate folders remain immutable evidence.

## Proposed Ownership Boundaries

- `sprites/player`: player presentation only.
- `sprites/monsters`: normal encounter presentation keyed by existing monster ID.
- `sprites/elites`: explicit elite visual overrides; absence falls back to normal monster art or current placeholder.
- `sprites/bosses`: boss presentation keyed by existing boss ID.
- `effects`: short presentation-only feedback keyed by an already-resolved existing effect/result.
- `ui/frames`: decorative scalable presentation; content and controls remain HTML.
- `ui/icons`: supplementary status icons; labels and numeric values remain readable HTML.
- `backgrounds`: static scene layers behind readable UI.
- `events`: illustrations only; event choices, rewards, and state remain existing HTML/game logic.

## Future Runtime Module Boundaries

Phase 71F may introduce a small typed asset catalog and reusable visual components only after explicit authorization. Planning requirements:

- One catalog entry per logical asset ID.
- One source path per catalog entry; targeted and obsolete candidates cannot both be registered.
- Asset-load failure must fall back to the current emoji/CSS presentation without crashing.
- Sprite rendering must accept explicit frame metadata rather than infer frame count from image width.
- Animation completion callbacks must not resolve combat, rewards, answer checking, or navigation.
- Reduced-motion mode must show a stable representative frame and preserve all gameplay feedback in text.
- Background and card-frame components must remain optional wrappers, not required data dependencies.

No catalog, component, import, or metadata file is created in Phase 71E.

## Proposed Controlled Integration Order

1. **Static battle identities**: Word Mage idle plus Slime, Bat, Goblin, Crystal Slime, and Gatekeeper idle, all with current placeholder fallbacks.
2. **Battle reactions**: hit, attack, and defeat sheets driven only by already-resolved battle state.
3. **Result effects**: elemental, shield, and upgrade effects after existing result/purchase resolution.
4. **Supplementary icons**: Gold, HP, and Shield while retaining text/value labels.
5. **Decorative surfaces**: vocabulary card frame and dungeon background after responsive/mobile layout QA.

Each stage should build and receive desktop/mobile smoke testing before the next stage. A stage may be rolled back to placeholders without affecting gameplay state.

## Integration Exclusions

Phase 71F should not silently expand scope to:

- Player defend, hurt, or victory animations that do not yet have approved candidates.
- Monster or boss identities without listed candidates.
- Event illustrations, because none are present.
- New boss specials, elements, attacks, rewards, or encounter rules.
- New persistence fields or save migrations.
- Animation-driven timing changes to questions, results, combat, shops, or progression.

## Recommendation

Proceed next to **Phase 71F Controlled Runtime Integration**, beginning with static battle identities and fallbacks. Require a separately stated implementation request before creating `src/assets/` or runtime code.
